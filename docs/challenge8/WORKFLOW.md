# Рабочий процесс роли verifast

Вход: [AGENTS.md](../../AGENTS.md). Текущее состояние и точные источники:
[STATUS.md](STATUS.md); исторические scope и результаты сохраняются в checkpoint
и Git-истории. Разрешённый объём каждой сессии определяет актуальное поручение.
Чтение или правка документации не разрешает новую техническую фазу, Cloud
execution или внешнюю публикацию.

## Ответственность и очередь

Proof-агент владеет доказательствами, контрактами SmallSort и соответствием
исходному Rust (source correspondence) своего направления. Роль `verifast`
сопровождает изменения инструмента, общие specs, review, минимальные примеры,
регрессии, интеграцию, поставки и будущие upstream-подачи. Вопросы на границе
spec/proof согласовывать с владельцем; перенос tool-патча не передаёт proof.
Основные агенты могут независимо продолжать эксперименты без ожидания review.

Очередь и история передачи хранятся здесь: `docs/challenge8/handoffs/<id>.md`,
одна карточка на изменение или воспроизводимый блокер, создаваемая при первом
поручении на его обработку. В карточке сохранять
последовательность событий и ссылки на точные commits/evidence; STATUS остаётся
коротким checkpoint роли, а не вторым реестром патчей. Большие логи/артефакты
хранить в разрешённом evidence-хранилище, фиксируя путь/URI и checksum.

Минимальные поля карточки (отдельный шаблон не нужен):

- ID, направление, цель, вызывающий код и фактический блокер;
- отправитель, источник: repo + полный опубликованный commit SHA + пути патча,
  upstream base и зависимости; отдельно статус проверки доступности;
- до/после передачи: активный repo/ветка/commit, ответственный и подтверждение
  передачи; соответствие исходного и перенесённого commits;
- минимальный пример, ожидаемое/фактическое поведение, гипотеза классификации,
  ресурсы/контракты и затрагиваемая семантика;
- профиль и рецепт воспроизведения; regression/evidence с Build ID и hashes
  либо NOT_RUN с причиной;
- review: reviewer, замечания, исправляющие SHA, открытые вопросы;
- отдельно candidate, regression, принятие каждым consumer и upstream-статус;
  ссылки на разрешение Cloud/публикации, если оно появилось.

## Получение и передача патча

1. Получить от proof-агента опубликованный commit `verify-rust-std`, точные
   пути, upstream base, зависимости и воспроизводимый блокер. Доступность
   commit проверить отдельно: наличие объекта на VPS не доказывает публикацию
   или доступность Cloud. Локальный непубликовавшийся источник допустим лишь
   как явно помеченный локальный кандидат с согласованным способом передачи.
2. Читать `git show <full-sha>:<path>` и историю точного commit; не переносить
   mutable working tree. Извлечь patch через `git show` или `format-patch`
   применительно к его формату. Патч-файл внутри proof-repo извлечь как blob;
   commit, меняющий непосредственно tool-код, переносить с явной фильтрацией
   путей. Не переносить случайно proofs, ledgers, evidence или pins.
3. В разрешённом задании применить изменение в локальной ветке VeriFast,
   проверить diff/base/зависимости и зафиксировать связь SHA. При необходимости
   адаптации записать её отдельно. Не править чужие proof-worktrees.
4. Явно согласовать момент передачи и единственное активное место разработки
   конкретного изменения. До подтверждения перенесённая копия — кандидат
   передачи, исходный владелец остаётся активным. После передачи исходная
   версия — исторический источник; дальнейшие правки tool-патча идут здесь.
   Если proof-агенту нужен новый эксперимент, явно завести отдельный variant
   или вернуть владение. Две расходящиеся копии не считать одним принятым патчем.
5. Интегрировать совместимые изменения с явным списком зависимостей. Review
   и возврат замечаний записывать в карточку; внешние сообщения отправлять
   только при явном разрешении.

## Review и evidence

Сначала различить ошибку инструмента, неподдержанную конструкцию, недостаточный
контракт и инфраструктурный сбой. Отказ верификатора не является основанием
менять семантику. Ошибки exporter/serializer/runner до проверки и timeout не
считать FAIL/PASS доказательства; хранить их как отдельную категорию. Выполненный запуск,
оборванный по лимиту времени, отмечать `INCOMPLETE_TIMEOUT`, а не `NOT_RUN`;
сам timeout не устанавливает дефект кандидата.

Проверять реальную obligation и caller, предусловия, соответствие исходнику,
отрицательные примеры и границу действующих гарантий. Не добавлять assumptions,
не ослаблять ownership/контракты/проверки и не снижать целевые гарантии ради PASS.
Для ownership/lifetime/kernel changes обязательны содержательное объяснение
сохранения ресурсов по путям, включая unwind/Drop где применимо, и независимое
review другим reviewer; самопроверка автора этого не заменяет.

Замечание должно указывать конкретный файл/символ/пример, нарушенное условие,
ожидаемое поведение и требуемую validation. Возвращать локальные замечания
активному владельцу; фиксировать исправляющий SHA и результат повторного review.
Незавершённый soundness-вопрос блокирует принятие, а не эксперимент на точном
candidate SHA.

Сохранять upstream требования из `README.txt`: стиль, просмотр diff, тест для
изменения поведения, build и test suite. Для технического принятия запускать
их в разрешённом Cloud, сначала минимальный пример и целевые регрессии, затем
нужный общий suite. Положительный тест дополнить отрицательным, когда меняется
граница допустимости. После достаточных checks не повторять их без причины.
Локальный экспериментальный commit до Cloud checks допустим как candidate
с NOT_RUN; такой commit не означает проверенную поставку. Для документационного
commit достаточно статических checks, компиляция и proof execution — NOT_RUN.

Различать четыре события, фиксируя каждое по exact SHA/profile:

| Событие | Что оно означает |
| --- | --- |
| Candidate подготовлен | Есть проверяемый diff и рецепт; регрессии могут быть NOT_RUN |
| Регрессии выполнены | Есть конкретные cases, команды, профиль и evidence; это не принятие consumer |
| Consumer принял pin | Его владелец независимо проверил свой caller/obligation и записал принятие |
| Upstream принял | Патч принят upstream с точным SHA; это не автоматическое принятие proof pin |

Классификация сохранённых логов и replay ранее полученного evidence не создают
нового proof credit. Изменившиеся source, семантика или профиль требуют новой
применимой проверки. Эксперимент можно продолжать до review на точном candidate
SHA; профиль этим не квалифицируется для итогового доказательства Challenge 8.

## Воспроизводимая версия и принятие pin

В карточке поставки фиксировать полный upstream base и tool commit, упорядоченный
состав patch-профиля/опции, точные specs, exporter, translator, Rust toolchain,
существенные зависимости/solver/container, команды и окружение сборки, hashes
артефактов, точные source/proof/infra commits, cases и Build IDs/evidence.
Для компонента внутри tool tree достаточно явно указать тот же SHA и путь;
для внешнего компонента нужен собственный pin. Сохранять известные ограничения,
статус review и NOT_RUN. Не использовать плавающий `latest`/`nightly` как proof
pin и не переписывать опубликованные версии; исправление получает новый SHA.

Потребитель проверяет точную версию, состав, происхождение и digest готового
комплекта, затем применимость существующих результатов tool-regressions.
В своей разрешённой фазе он выполняет затронутые интеграционные проверки
actual caller, source correspondence и гарантий. Пересборка инструмента или
повтор общих регрессий нужны при конкретной причине: изменении состава или
окружения, недостаточном evidence либо отдельной проверке воспроизводимости.
Повторное использование бинарника не переносит автоматически proof credit
на новый source/profile. Потребитель записывает accepted/rejected/pending с
exact pin и evidence в своём репозитории, а результат передачи — в нашей карточке.
Только proof-владелец меняет свой pin. До его принятия
предыдущий accepted pin сохраняет статус; наша поставка его не заменяет.
История использования исходного патча в экспериментальном proof-профиле
сохраняется отдельно от принятия новой поставки. Неизменённый перенос, новая
упаковка или переписанная только локальная PR-история не требуют автоматического
повторного принятия реализации proof-агентом для самостоятельной upstream-подачи.
Actual caller proofs остаются отдельной proof-задачей, если поручение не требует
их как зависимость конкретного изменения инструмента.

## Cloud и VPS

На VPS допустимы редактура, Git, чтение evidence, hashing и syntax/static
parsing. Исключение WORK-POLICY §4: малые изолированные executable tests
служебных classifiers/parsers на сохранённых логах или синтетических данных.
Сначала проверить entrypoint/imports; использовать уже установленный лёгкий
runtime и отдельный временный каталог. Не вызывать compiler/verifier,
proof runner, source extractor, dependency installer или Cloud dispatch;
не менять реальное evidence, чужие файлы и coordinator. Это не proof result.

Компиляция VeriFast/Rust, Cargo build/check/test, rustc, VeriFast, Kani/CBMC,
bootstrap/x.py, proof runners/extractors и полноценные tool-regressions выполняются
в Cloud, включая wrappers/containers. Не ставить тяжёлые build dependencies
на VPS. GitHub Actions также требуют отдельного явного разрешения.

Стабильный owner — `verifast`. Перед новой фазой и первым Build нужны отдельное
разрешение на фазу, её собственный бюджет и ledger, проверенная lane и подключение
к **существующему** coordinator. Исторические бюджеты, deadlines и разрешения
`merge`/`select-sort4` не переходят этой роли. Точные infra/proof SHAs обязательны.
Документация не разрешает создавать регистрацию, менять dispatcher или coordinator.
Передавать Cloud committed Git objects с сохранением исходных commit/tree/blob
идентичностей; не передавать GitHub credentials, рабочее дерево, config или hooks
как build input. Доступность такого входа проверять отдельно от наличия GitHub-форка.

Действующий протокол описан в proof-repo: `research/challenge-8/cloud-build/README.md`
и `PARALLEL-BUILDS.md`; клиенты — `control.py`/`coordination.py`. Shared state:
`/root/smallsort-ci-coordination/active.json`, lock: соседний `lock`. При активном v2 максимум два queued/running/unresolved Cloud Build суммарно,
один на owner и ledger. Подготовленный v3 допускает три стабильных owners
(select-sort4, merge, verifast) и три слота только после подтверждения всех
клиентов и миграции под общим lock; старый клиент обязан отказать на новом
протоколе. Активные записи не удалять и не обнулять. Точный переносимый commit
и порядок принятия сохранены в [Cloud checkpoint](cloud/verifast-mdnew-validation-20261009.md).
Request носит advisory-характер; admission и token reservation обязательны.
Неопределённый submit занимает слот до terminal API evidence или окончательного
подтверждения отказа; timeout клиента не разрешает повторный submit/снятие слота.
Чужие reservations/ledgers не исправлять. Перед разрешённым Cloud-заданием
перечитать актуальный протокол из точного commit; старые single-slot правила
не применять вместо согласованного v2. Статус Cloud конкретной сессии
фиксируется в STATUS и карточке.

## Upstream и временная работа без форка

Готовить необходимые зрелые патчи заранее: минимальный reproducer, объяснение
проблемы и сохранения soundness, отдельные focused commits, tests, evidence,
описание зависимостей и черновик PR. Upstream acceptance может повлиять на сроки
итоговой квалификации Challenge 8; обязательность со стороны организаторов
**пока не установлена**. Не откладывать подготовку до окончания всех proofs.

Наличие форка и доступ к GitHub фиксируются в STATUS, а разрешённые действия —
в актуальном поручении. Upstream push, создание форка, issues/PR и внешние
сообщения требуют отдельного явного разрешения в поручении/карточке. Готовый
черновик и чтение этих инструкций его не выдают. Перед upstream-публикацией
пользователь отдельно review/approve точные head commit и PR body; существенное
изменение требует повторного review. Подготовка пакета сама по себе не разрешает
даже draft PR, публичный форк, PR-ветку, issue, comment или сообщение сопровождающему.
После разрешения отслеживать upstream, связывать принятые SHA с местными патчами
и удалять заменённые обходы через review и regression/consumer acceptance.

Канал публикации review-пакетов: при прямом разрешении в актуальном поручении
добавить `research/verifast-review/<полный-SHA-checkpoint>/` в репозитории
`Tiramisu-Cake/verify-rust-std`, ветке `review/verifast`. Сохранить прежние пакеты
и историю; использовать Git plumbing, обновляя только свои служебные refs и
`review/verifast`, без изменения index, checkout и рабочих файлов proof-агентов.
Добавлять пакет поверх актуальной remote-головы, без force-push. Проверить remote
SHA, доступность через авторизованный GitHub API и hashes файлов; при отказе push
сохранить проверенный ZIP с точной причиной и абсолютным путём. Пакет содержит
README, актуальные AGENTS/WORKFLOW/STATUS, карточку review, исходный патч/tool diff,
tests/черновик PR при наличии, Cloud-план и manifest с точными SHA и hashes.
Публикация по этому каналу не разрешает upstream-публикацию, изменение main,
consumer pins, чужих proof-worktrees, coordinator или ledgers. Разрешение и
scope конкретной публикации фиксируются в STATUS и карточке.

Локальный commit не считать опубликованным или доступным Cloud без проверки.
При необходимости сохранять контрольный Git bundle с перечнем refs и checksum;
копия на этом VPS не является внешним резервированием. Не переписывать чужую
историю, не делать force-push/reset и не менять глобальную Git-конфигурацию.
Организационные документы держать отдельно от подаваемых upstream code commits.

## Сессия и делегирование

В начале зафиксировать scope, timebox, каталог, Git status/ветку/HEAD/remotes,
источники инструкций и незавершённые карточки. Выбрать одну реальную obligation
и caller для технического задания. Обычно окно — 60 минут, ещё максимум 30
только на завершение начатого и checkpoint; конкретное поручение может его менять.
Не заполнять оставшееся время новой фазой без разрешения.

Перед завершением проверить diff, relative links, согласованность разрешений,
отсутствие посторонних изменений, сохранить только свои файлы отдельным локальным
commit. Checkpoint содержит exact commits/profile, выполненные проверки,
proof/replay/NOT_RUN отдельно, blockers и одно рекомендуемое следующее задание.
Не включать чужие изменения в commit и не устранять их для «чистого» status.

Использовать explorer для существенного чтения и worker для существенной
реализации после выбора поведения и границ. По умолчанию subagent GPT-6 Luna;
для сложного локального анализа повышать reasoning, для архитектурных решений
и неоднозначного review выбирать GPT-6 Sol, Astra — только для особенно трудного.
Не делегировать мелкие edits/поиски. Worker получает цель, scope, acceptance
criteria, invariants, validation и non-goals; неоднозначности возвращает main
agent. Параллельные writes допустимы только в независимых областях; у изменения
один активный владелец. Main agent отвечает за решения, интеграцию, validation
и отчёт; не повторяет исследование explorer без конкретной причины.
