# Challenge 8: сопровождение VeriFast

Обязательная точка входа для роли `verifast`. Здесь сопровождаются изменения
VeriFast, общие specs и воспроизводимые поставки инструмента для двух
proof-направлений Challenge 8: select/sort4 и merge/guard/Drop/insertion/fallback.
Основные агенты продолжают свои экспериментальные доказательства и патчи;
они не обязаны передавать всю разработку или ждать нашего review.

## Первые чтения и границы

1. Прочитать текущее поручение, этот файл, [WORKFLOW](docs/challenge8/WORKFLOW.md)
   и [STATUS](docs/challenge8/STATUS.md). Чтение инструкций **не разрешает новую
   фазу** разработки, review, вычислений или публикации.
2. Проверить каталог, Git status, ветку, HEAD, remotes и незавершённую передачу.
   Сохранить изменения пользователя; не делать reset/force-push, не менять
   глобальную Git-конфигурацию. Новые clones/worktrees — только по необходимости.
3. По точным коммитам proof-репозитория прочитать `AGENTS.md`,
   `research/challenge-8/WORK-POLICY.md`, `COMPLETION-PLAN.md`, checkpoint нужного
   направления и описание coordinator. Начальные пути и версии — в STATUS.
   Записать версии чтений; при расхождении правил следовать явному поручению,
   а существенную неясность разрешить до зависимых действий.
4. Для разрешённой технической задачи прочитать upstream [README.txt](README.txt),
   [src/README.txt](src/README.txt), [README.Linux.md](README.Linux.md) и нужные
   инструкции подсистемы. Сохранять upstream style, тестовые требования и
   дисциплину symbolic execution; проектные правила не заменяют их документацию.

Доказательства, контракты SmallSort и source correspondence принадлежат
proof-агентам в `verify-rust-std`. Их деревья читать через точные коммиты;
не переключать ветки и не менять index, файлы, remotes, ledgers или pins.
Здесь править только в рамках поручения; при переносе патча явно закреплять
единственного активного владельца и место разработки по WORKFLOW.

## Вычисления, версии и завершение

На VPS разрешены редактирование, Git, чтение evidence, hashing, syntax/static
parsing и только малые изолированные tests служебных классификаторов по
WORK-POLICY. Компиляция VeriFast/Rust, proof execution и полноценные регрессии —
только в Cloud; тяжёлые build dependencies на VPS не устанавливать.
Будущему owner `verifast` нужны отдельные разрешённые фаза, бюджет, ledger и
подключение к существующему coordinator: максимум два queued/running/unresolved
Build суммарно и один на owner/ledger. Исторические бюджеты не наследуются.

Использовать точные SHA и состав профиля, различать candidate, regression,
consumer acceptance и upstream acceptance. Не ослаблять проверки ради PASS;
ownership/lifetime/kernel changes требуют объяснения сохранения ресурсов и
независимого review. Эксперимент на candidate SHA не квалифицирует профиль
для итогового доказательства; старое evidence не становится новым proof result.

По умолчанию окно — 60 минут; ещё максимум 30 только на завершение начатого
и checkpoint, если поручение не задаёт иное. В начале выбрать разрешённую
задачу; в конце проверить diff/ссылки/границы, выполнить допустимую validation,
сохранить локальный commit и checkpoint с точными версиями и NOT_RUN.
Организационные commits держать отдельно от будущих upstream-патчей.
Если задача закончена раньше, завершить сессию без новой фазы.

Локальные ветки/commits/bundles допустимы в рамках актуального поручения.
Upstream push, issues/PR, форк и внешние сообщения требуют отдельного явного
разрешения; этот файл его не выдаёт. Канал review-пакетов в `verify-rust-std`
описан в WORKFLOW и используется только при разрешении в текущем поручении;
он не разрешает менять main или принимать consumer pin.

Делегировать существенное независимое чтение/реализацию встроенным subagents,
когда это экономит контекст или время; мелкие задачи делать напрямую.
Выбор модели, контракт worker и ответственность main agent — в WORKFLOW.
